## 🧭 О проекте

**Ростелеком Умный склад** — это решение для кейс-чемпионата "Расти в ИТ".  
Проект направлен на автоматизацию и повышение эффективности управления складом с использованием **RTK-технологий, анализа данных** и **AI-моделей** для прогнозирования и оптимизации логистических процессов. 
[📂 Ссылка на кейс](https://drive.google.com/drive/u/0/folders/16xJ4XcN_ipFjO-VJEkBTMvxk1MhP9xqA)

Система объединяет **данные RTK-устройств**, **машинное обучение** и **умный интерфейс**, чтобы:
- Оптимизировать хранение и перемещение товаров  
- Повысить точность позиционирования техники и персонала  
- Предсказывать загрузку и узкие места склада  
- Автоматизировать управленческие решения  

---
Два окружения: **dev — локально с hot reload**, **prod — на сервере с HTTPS через Caddy**.

## Быстрый локальный запуск

Запустите Docker Desktop, затем из папки проекта выполните:

```sh
make dev
```

Команда сама создаёт `.env.dev` из шаблона, если файла ещё нет, собирает образы и ждёт готовности приложения. Существующий `.env.dev` сохраняется. Одноразовый сервис `dev-init` применяет миграции к пустой БД, создаёт недостающий realm и клиент Keycloak, сервисного администратора и пользователя для входа. В пустую БД добавляются два склада, три товара, робот и история операций за 30 дней. При повторном запуске данные и пароли не сбрасываются.

Откройте **http://localhost:5173**, войдите как **`admin@example.com` / `dev-admin-123`** и выберите «Демонстрационный склад». Можно добавлять склады, товары и роботов, смотреть сканирования, историю и поставки. Worker запускает эмуляцию робота, scheduler создаёт отгрузки и прогнозы, поэтому остатки и показатели меняются со временем. Данные сохраняются после остановки.

API: http://localhost:8000/docs. Остановка: `make dev-down`. Повторный запуск без сборки: `make dev-up`.

Учётная запись задаётся через `DEV_LOGIN_EMAIL` / `DEV_LOGIN_PASSWORD` в `.env.dev` при первом создании. Изменение этих параметров не меняет пароль уже существующего пользователя Keycloak. Готовые пароли и демоданные используются **только в dev**; `compose.prod.yaml` не содержит `dev-init`.

## Файлы запуска

|---|---|

| `compose.prod.yaml` | Production-образы, Caddy и HTTPS |

| `frontend/Dockerfile` | Сборка Vite для dev и статики с nginx для prod |

| `docker/caddy/Caddyfile` | Домены, HTTPS и маршрутизация prod |
| `.env.dev.example`, `.env.prod.example` | Шаблоны параметров двух окружений |
| `.env.dev`, `.env.prod` | Локальные значения и секреты; не хранятся в Git |

Зависимости фиксируются в `pyproject.toml` + `uv.lock` и `frontend/package.json` + `frontend/package-lock.json`. Миграции находятся в `alembic/`, модель прогноза — в `models_store/`, данные для разработки — в `fixtures/` и `backend/ml/demo_ml_data/`.

## Порты

| Сервис | Dev: адрес на компьютере | Адрес внутри Docker | Prod: доступ снаружи |
|---|---|---|---|
| Frontend | http://localhost:5173 | `frontend:5173` / `frontend:80` | `https://APP_DOMAIN` |
| API | http://localhost:8000/docs | `api:8000` | Через Caddy: `/api/...`, `/docs` |
| PostgreSQL | `localhost:5433` | `db:5432` | Нет |
| Redis | `localhost:6380` | `redis:6379` | Нет |
| Keycloak | http://localhost:8080 | `keycloak:8080` | `https://KEYCLOAK_DOMAIN` |
| БД Keycloak | `localhost:5434` | `keycloak-db:5432` | Нет |
| Caddy | Не запускается | `80`, `443` | `80/tcp`, `443/tcp` |

Worker и scheduler не имеют входящих портов. `dev-init` — одноразовая подготовка; статус `Exited (0)` для него означает успех. Порт healthcheck Keycloak `9000` не публикуется. Все порты dev привязаны к `127.0.0.1`.

В `127.0.0.1:5433:5432` порт `5433` принадлежит компьютеру, а `5432` — контейнеру. Порты компьютера меняются через `DEV_*_PORT` в `.env.dev`; адреса `db:5432`, `redis:6379`, `api:8000` остаются прежними. Frontend обращается к `/api` на текущем сайте, WebSocket использует `ws` локально и `wss` при HTTPS.

## Команды

Нужны Docker с Compose v2 и Make. Команды выполняются из папки с этим README.

Для dev `.env.dev` создаётся автоматически из `.env.dev.example`. Для prod скопируйте `.env.prod.example` в `.env.prod`. Если файлы уже существуют, сравните их с шаблонами и сохраните свои значения. Prod требует реальных доменов, паролей и тегов образов `BACKEND_IMAGE` / `FRONTEND_IMAGE`.

| Действие | Dev | Prod |
|---|---|---|
| Проверка настроек без вывода секретов | `make dev-config` | `make prod-config` |
| Сборка образов | `make dev-build` | `make prod-build` |
| Запуск готовых образов | `make dev-up` | `make prod-up` |
| Состояние | `make dev-ps` | `make prod-ps` |
| Логи | `make dev-logs` | `make prod-logs` |
| Остановка с сохранением данных | `make dev-down` | `make prod-down` |
| Миграции подготовленной БД | `make dev-migrate` | `make prod-migrate` |

`make dev` объединяет сборку, первичную настройку и запуск с ожиданием готовности. `*-up` не собирает образы. Для других команд используйте, например:

```sh
make dev-compose ARGS="up -d db redis keycloak-db keycloak"
make dev-compose ARGS="restart worker scheduler"
make prod-compose ARGS="logs --tail=100 api"
make prod-compose ARGS="pull"
```

`pull` нужен только для уже опубликованных образов из registry. После изменения зависимостей пересоберите образы. API перезагружается при изменениях `backend/`, Vite — при изменениях frontend; worker и scheduler нужно перезапускать. Dev монтирует `frontend/src`, `public`, `index.html` и `vite.config.ts`; изменения других конфигураций frontend требуют пересборки. Python-зависимости находятся в `/opt/venv` и не перекрываются bind mounts.

Без Make команды эквивалентны:

```sh
# Пример запуска dev
 docker compose --project-name rtk-smart-warehouse-dev --env-file .env.dev -f compose.yaml -f compose.dev.yaml up -d --no-build
# Пример запуска prod
 docker compose --project-name rtk-smart-warehouse-prod --env-file .env.prod -f compose.yaml -f compose.prod.yaml up -d --no-build
```

`--env-file` подставляет параметры в Compose; `env_file` в overlay передаёт параметры backend-процессам. Обычный `.env` в Docker-запуске не используется; существующий файл служит настройкам Python при запуске вне Docker. `ENV_FILE` и старые `KC_DB_*` / `KC_HOSTNAME` в env-файлах не нужны: настройки сервера Keycloak заданы в Compose. Переменные shell имеют приоритет при подстановке Compose.

После редактирования `.env.dev` / `.env.prod` выполните соответствующий `*-up`: простой `restart` не применяет новые переменные. Изменение пароля в env не меняет пароль в существующей БД.

## Первое развёртывание prod

1. Заполните `.env.prod`, проверьте конфигурацию и соберите образы.
2. Поднимите инфраструктуру: `make prod-compose ARGS="up -d db redis keycloak-db keycloak"`.
3. Для новой пустой БД выполните `make prod-migrate`: baseline создаёт исходные таблицы, затем применяются следующие миграции. Существующая БД с корректной историей Alembic продолжает свою цепочку без повторного создания таблиц. Старую схему без истории Alembic нужно отдельно сопоставить с миграциями перед переносом.
4. Создайте или импортируйте realm и клиент из `.env.prod` в Keycloak. Для текущего входа нужен Direct Access Grants и scopes `openid profile email`. Чтобы передавать прикладную роль, добавьте mapper realm roles в `userinfo` с claim `realm_access.roles`. Заполните `KEYCLOAK_CLIENT_SECRET`, `KEYCLOAK_ADMIN_USERNAME`, `KEYCLOAK_ADMIN_PASSWORD` (администратор realm).
5. Запустите весь контур через `make prod-up`. Демоданные и локальные учётные записи здесь не создаются.

В prod направьте оба домена на сервер и откройте TCP `80/443`. Для первоначального доступа к консоли Keycloak после подготовки БД выполните `make prod-compose ARGS="up -d --no-build caddy"`: запустятся Caddy и его зависимости API/frontend. Caddy получает TLS-сертификаты автоматически. Образы должны соответствовать архитектуре сервера.

Production-сборка frontend выполняет `tsc -b` и `vite build`. Ошибки неиспользуемых импортов и переменных устранены; проверка типов остаётся включённой.

Dev и prod используют разные имена проектов и отдельные тома. Данные старого проекта `rtk-smart-warehouse` автоматически не переносятся: для перехода требуется резервная копия и восстановление. Перед обновлениями БД остановите процессы записи и сделайте резервную копию. Команды `*-down` сохраняют тома БД, Redis, ML-моделей и сертификатов.

## Структура backend

```text
backend/
  api/            HTTP и WebSocket: маршруты, зависимости, перевод ошибок в HTTP
  service/        прикладные сценарии и границы транзакций
  ports.py        Protocol-интерфейсы репозиториев, транзакции, Keycloak и прогнозирования
  domain/         ошибки, статусы и независимые от ORM структуры данных
  repositories/   SQLAlchemy-запросы; без commit / rollback / HTTP-ошибок
  db/             фабрика сессий и SQLAlchemy-адаптер транзакции
  models/         таблицы и связи SQLAlchemy
  schemas/        проверка входных данных и форматы ответов
  integrations/   адаптер Keycloak
  scheduler/      фоновые задания и их запуск
  workers/        запуск фоновых обработчиков
  robot_emulator/ эмуляция роботов
  ml/             модели прогнозирования и доступ к обучающим данным
  ws/             публикация событий и WebSocket
```

Поток обычного запроса: **router → service → Protocol → SQLAlchemy repository**. Конкретные реализации собираются в `api/deps.py`; все репозитории одного запроса получают одну сессию. Сервисам не нужен импорт SQLAlchemy, ORM-моделей или FastAPI.

Изменяющий сценарий выглядит так:

```python
async with self.transaction:
    user = await self.user_repo.create(data)
    await self.kkid_user_repo.create(keycloak_id, user.id)
    await self.transaction.commit()
```

Репозиторий может вызвать `flush`, чтобы получить ID или проверить ограничения, но данные ещё не подтверждены. Сервис явно вызывает `commit` после всех операций. Адаптер `SqlAlchemyTransaction` откатывает незавершённую операцию при исключении или отмене задачи и переводит ошибки ограничений БД в ошибки приложения. Обычный `session.begin()` внутри репозитория больше не используется — иначе отдельный запрос мог незаметно завершить часть общего сценария.

`domain/entities.py` содержит структурные интерфейсы записей. SQL-реализация возвращает ORM-объекты, а тестовая — обычные объекты с нужными полями. Сервисы не вызывают методы ORM и не зависят от отслеживания изменений; запись выполняется методами репозиториев. При замене хранилища потребуется новый адаптер этих интерфейсов, включая семантику блокировок `lock_many` / `get_for_update`, и новая реализация транзакции.

`NotFound`, `Conflict`, `InvalidOperation`, `RelatedEntityError` и `StorageError` переводятся в HTTP в `api/errors.py`. SQLSTATE и детали SQL остаются в адаптере БД. Keycloak находится за интерфейсом `IdentityProvider`, прогнозирование — за `PredictorFactory`. Хеширование пароля также можно подменить при тестировании.

### Исправленные сценарии

- Товар и счётчики складов сохраняются одной транзакцией. Перенос с неизменным количеством учитывает оба склада; блокировки берутся в определённом порядке. Ошибка вместимости или сохранения откатывает операцию.
- PATCH товара действительно частичный: пропущенные поля сохраняются, отрицательные остатки отклоняются. Вместимость склада нельзя уменьшить ниже текущего остатка.
- Пользователь и связь Keycloak сохраняются атомарно. При регистрации неуспешная запись в БД компенсируется удалением созданного пользователя Keycloak. Если компенсация не удалась, это логируется; общей транзакции между двумя системами нет.
- Роль при первом входе выбирается явно: `admin`, если такая роль есть в realm, иначе `user`. Системные роли Keycloak и позиция роли в списке не задают права приложения. Другие прикладные роли нужно явно добавить в эту политику.
- Создание/удаление поставок и отгрузок управляется сервисами; добавлены методы, которые уже вызывались существующими маршрутами. Исправлена подмена `warehouse_id` на `product_id` при создании позиции поставки.
- Плановая поставка вынесена из HTTP-обработчика в сервис. Повтор идентичного запроса возвращает тот же план, повтор ID с другими данными — конфликт; товар должен относиться к указанному складу.
- Разбор CSV и генерация PDF/Excel перенесены из репозитория в сервис. Ошибочная строка CSV теперь явно отклоняет весь импорт вместо пропуска строки или подстановки нулевого количества.
- Сохранение прогнозов исправлено: ранее вставка была недостижима из-за отступов; добавлены отсутствовавшие SQL-операции. Дробная вероятность прогноза больше не проверяется как целое число.
- Плановая отгрузка откатывается при ошибке и обновляет счётчик склада вместе с остатками. Ключ блокировки одинаков для разных процессов; блокировка снимается самой БД при завершении транзакции. Коммита в `finally` больше нет.
- Удалены неиспользуемые дубли сервисных функций и провайдеров, дубли методов истории роботов и сломанный неиспользуемый middleware. Создание БД/engine отложено до реального обращения к данным.

Это разделение прикладных сценариев, а не обещание смены всей БД одной настройкой. Сложные запросы, модели и миграции остаются в SQLAlchemy. Эмулятор, ML-доступ к данным и часть фоновых заданий по-прежнему содержат специализированный SQL-код. Добавленная baseline-миграция создаёт исходную схему для новой БД.

## Тесты backend

Быстрые тесты сценариев и HTTP работают без PostgreSQL, Redis и Keycloak:

```sh
uv run --frozen python -m pytest tests/unit -q
# Или после make dev-build:
make test
```

В тестах используются маленькие реализации репозиториев в памяти и `AsyncMock`. Проверяются остатки и вместимость, переносы, откаты, отмена операции, пользователь и Keycloak, поставки/отгрузки, планирование, CSV, отчёты и прогнозы. Архитектурные тесты запрещают транзакции в репозиториях и импорты SQLAlchemy/FastAPI в сервисах.

Для HTTP есть `create_app(start_background=False)` и стандартные `app.dependency_overrides`: проверяется настоящий маршрут без фоновых задач, а зависимости можно заменить сервисом или тестовой сессией.

Интеграционные тесты используют настоящий PostgreSQL. Они создают отдельную случайную схему для каждого теста и удаляют её после завершения. Разрешена только явно указанная тестовая БД с именем `rtk_test*`:

```sh
docker run --rm -d --name rtk-test-db \
  -e POSTGRES_DB=rtk_test -e POSTGRES_USER=rtk_test -e POSTGRES_PASSWORD=rtk_test \
  -p 127.0.0.1:55432:5432 postgres:16-alpine
# Дождитесь готовности: docker exec rtk-test-db pg_isready -U rtk_test
TEST_DATABASE_URL=postgresql+asyncpg://rtk_test:rtk_test@127.0.0.1:55432/rtk_test \
  uv run --frozen python -m pytest -q
docker stop rtk-test-db
```

Без `TEST_DATABASE_URL` интеграционные тесты явно пропускаются. Проверяются реальные commit/rollback, FK/уникальность, сохранение через HTTP, повтор плановой поставки, откат удаления позиций и конкурентное изменение вместимости. Большинство тестов создают схему из ORM-моделей. Отдельный интеграционный тест выполняет всю цепочку миграций на пустой схеме, сравнивает её с ORM и проверяет downgrade/повторный upgrade. Другой тест проверяет, что повторная загрузка демоданных сохраняет изменения пользователя. Реальный Keycloak и длительная работа эмулятора не входят в этот набор тестов.


## CI — проверки pull request

Workflow `.github/workflows/ci.yml` запускается при создании PR в `main`, новых коммитах в этом PR и его повторном открытии. После попадания workflow в основную ветку его также можно запустить вручную во вкладке Actions → CI → Run workflow.

1. **Backend tests** устанавливает зависимости из `uv.lock` с Python 3.12 и запускает весь `pytest`, включая интеграционные проверки с отдельным PostgreSQL 16. БД называется `rtk_test_ci` и существует только на время задания.
2. После успешных тестов параллельно выполняются **Build backend** и **Build frontend** — сборка цели `production` из соответствующих Dockerfile для `linux/amd64`. Сборка frontend включает TypeScript.

Новый коммит отменяет незавершённый запуск того же PR. Зависимости и слои Docker кешируются. Actions закреплены на конкретных commit SHA. Workflow использует `pull_request`, права `contents: read` и тестовые учётные данные; `.env.dev`, `.env.prod`, Keycloak и production-секреты ему не нужны. Образы проверяются сборкой и не публикуются в registry; deployment в этом workflow отсутствует.

Для активации отправьте изменения проекта, включая `.github/workflows/ci.yml`, в GitHub и откройте PR в `main`. Результаты появятся в PR → Checks и во вкладке Actions.

Чтобы не допускать merge при ошибках, после первого запуска создайте активный ruleset для `main` в Settings → Rules → Rulesets. Включите **Require a pull request before merging** и **Require status checks to pass**, добавив проверки `Backend tests`, `Build backend`, `Build frontend`. Сам workflow не изменяет настройки защиты ветки.
